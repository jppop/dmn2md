# dmn2md — DMN → Markdown Converter for Claude Code

## Project context
Go CLI tool that parses DMN (Decision Model and Notation, XML format) files
and generates structured Markdown for easier reading, optionally usable as Claude Code skills or rules (the output format is selected via a CLI option).

Go module: `github.com/jppop/dmn2md`

Developer: experienced Java background, beginner in Go.

## Target DMN model

DMN is XML. Main structure to parse:
- `<definitions>` → root
- `<decision>` → a decision table
- `<decisionTable hitPolicy="...">` → contains inputs, outputs, rules
- `<input>` / `<output>` → columns (with `label` and `inputExpression`)
- `<rule>` → one row = N inputEntry + M outputEntry

XML namespace: `https://www.omg.org/spec/DMN/20191111/MODEL/`

## Markdown Output Format

The generated Markdown must follow this structure (one file per DMN file):

```markdown
# Spécification DMN — <definitions name>

> Generated by `<tool name>`

- **Namespace** : <namespace>

---

## Decision Requirements Diagram

<Mermaid flowchart describing the DRD
Nodes: decisions (rectangle) and input data (stadium shape)
Edges: informationRequirement arrows (decision → decision)
>

## Decisions

One section per decision, in dependency order (leaves first):

### <decision name>

- **Type** : <decision type (Literal Expression or Decision table)>
- **ouput** : <lit of ouput variables with their type in parenthesis>
- **input** : <list of input variables>
- dependencies : <list of dependent decision, if applicable>

<for the decision table:
The Hit policy and a table with the input and the ouputs.
Followed by the list of allowed values used in the decision
>
<for the literal expression:
a FEEL code block with the expression implementation
>

## Dictionnaire de données

<all inputs and outputs across all decisions rendered as a table>

```

Example of result file: @.claude/decision-sample.md

## Rendering rules
- "-" entries render as `*` (any value)
- Strings in FEEL keep their double quotes: `"active"`
- Decisions are rendered in topological order (dependencies first)
- The Mermaid diagram uses `flowchart TD`
- Input data nodes (no decision logic) use `([name])` shape
- Decision nodes use `[name]` shape
- Arrows represent informationRequirement: dependency --> decision

## Go conventions
- Explicit error handling: always `if err != nil`, never ignore with `_`
- No `interface{}` / `any` when a concrete type is possible
- Structs with XML tags for parsing: `xml:"tagName"`
- Tests with testify: `assert.Equal`, `require.NoError`
- Golden files for rendering tests (compare output with expected file)

## What not to do
- Do not use `panic()` except for genuine internal bugs (≠ user errors)
- Do not ignore errors with `_` on I/O
- Do not put business logic in `main.go`
